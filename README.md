# NYC Taxi 실시간 운행 모니터링 데이터 파이프라인


## 1. 프로젝트 목표

NYC Yellow Taxi의 과거 운행 기록을 실시간 운행 이벤트처럼 재생하여 

대량의 모빌리티 이벤트를 수집·처리하는 스트리밍 파이프라인을 구축한다. 

이를 통해 지역·시간대별 택시 이용 현황과 현재 운행 상황을 모니터링하고,

차량 운영 의사결정을 위한 데이터를 제공하는 것을 목표로 한다.

파이프라인을 통해 다음과 같은 운영 지표를 생성한다.
- 현재 운행 중인 Trip 수
- 최근 일정 시간 동안의 승차 발생 건수
- 지역별 승차 및 하차 건수
- 시간대별 택시 이용량
- 평균 운행 시간
- 평균 운행 거리
- 평균 운임
- 현재 이용량과 과거 동일 시간대 이용량 비교

최종적으로 모빌리티 운영자가 시간대 및 지역별 택시 이용 현황을 파악하고 

차량 공급·배치 등의 운영 의사결정에 참고할 수 있는 데이터를 제공하고자 한다.

## 2. 프로젝트 선정 이유

모빌리티 서비스에서는 다수의 차량 운행 정보가 지속적으로 발생하며,
이러한 데이터를 안정적으로 수집·처리하고 운영에 활용할 수 있는 형태로 가공하는 데이터 파이프라인이 중요하다.

NYC Yellow Taxi 데이터는 실제 택시 운행에서 발생한 대규모 데이터로,
승차·하차 시각, 출발·도착 지역, 운행 거리, 요금 등 운행 흐름을 분석할 수 있는 정보가 포함되어 있다.

특히 승하차 시각 정보가 존재하기 때문에 이미 저장된 과거 운행 데이터를 시간 순서대로 재생하여
실제 차량 운행 이벤트가 지속적으로 발생하는 환경을 모사할 수 있다고 판단했다.

따라서 본 프로젝트에서는 NYC Yellow Taxi 데이터를 이용해 과거 운행 기록을 실시간 이벤트 형태로 재구성하고,
Kafka, Spark 등을 활용하여 수집 → 처리 → 저장되는 데이터 파이프라인을 직접 구현하고자 한다.

최종적으로는 지역·시간대별 택시 이용 현황과 운행 지표를 제공하여
모빌리티 운영자가 차량 운영 의사결정에 참고할 수 있는 데이터 구조를 만드는 것을 목표로 한다.

## 3. 사용할 데이터셋

* 사용할 데이터: NYC TLC Yellow Taxi Trip Record Data 2025년 1월
* 출처: NYC Taxi & Limousine Commission
* 파일 형식: Parquet
* 데이터 크기: 약 347만 건

## 4. 데이터 파이프라인 초안

본 프로젝트는 NYC Yellow Taxi의 과거 운행 데이터를 실제 택시 운행 이벤트가 발생하는 것처럼 재생하여 수집·처리하는 모빌리티 운영 데이터 파이프라인을 구현하는 것을 목표로 한다.

전체 데이터 흐름은 다음과 같이 구성한다.

```text
NYC TLC Yellow Taxi
2025년 1월 Parquet 데이터
        ↓
Python Replay Producer
과거 운행 기록을 시간 순서대로 이벤트화
        ↓
Apache Kafka
taxi-trip-events 수집 및 전달
        ↓
Spark Structured Streaming
실시간 데이터 정제 및 집계
        ↓
PostgreSQL / Parquet
집계 결과 및 가공 데이터 저장
        ↓
Open Source BI Dashboard
지역·시간대별 운행 현황 시각화
        ↓
모빌리티 운영 의사결정 지원
```

Airflow는 배치 집계, 작업 스케줄링, 실패 작업 재시도 및 파이프라인 실행 관리를 위해 활용할 예정

## 5. 처리해보고 싶은 내용

### 실시간 운행 현황
- trip_started와 trip_completed 이벤트를 이용하여 현재 운행 중인 Trip 수 계산
- 최근 일정 시간 동안 발생한 승차 및 하차 건수 확인

### 지역·시간대별 택시 이용량
- 시간대별 승차 건수 집계
- 지역별 승차 및 하차 건수 집계
- 택시 이용이 집중되는 지역과 시간대 파악

### 운행 지표
- 평균 운행시간
- 평균 운행거리
- 평균 운임
- 평균 최종 결제금액

### 운영 데이터 활용
- 현재 이용량과 과거 동일 시간대 이용량 비교
- 특정 지역의 이용량 증가 여부 파악
- 지역·시간대별 차량 수요를 파악하여 차량 공급 및 배치 등의 운영 의사결정에 활용

### 장애 상황 테스트

실제 모빌리티 환경에서는 네트워크 장애나 시스템 오류로 인해 운행 데이터가 늦게 도착하거나 중복·누락될 수 있다.

따라서 정상적인 데이터 처리뿐만 아니라 일부러 장애 상황을 만들어 파이프라인이 데이터를 안정적으로 처리할 수 있는지도 확인해보고자 한다.

예를 들어 다음과 같은 상황을 테스트한다.

- 네트워크 문제를 가정하여 이벤트 전송을 일시적으로 중단
- 네트워크 복구 후 전송하지 못한 이벤트를 다시 처리할 수 있는지 확인
- 동일한 운행 이벤트를 중복으로 전송했을 때 중복 집계 여부 확인
- Kafka 또는 데이터 저장 과정에 일시적인 장애가 발생했을 때 데이터 유실 여부 확인

프로젝트 초기에는 네트워크 중단·복구와 중복 이벤트 처리 등 간단한 장애 상황부터 구현하고, 이후 가능한 범위에서 장애 테스트를 확장한다.

## 6. 사용해보고 싶은 기술

| 기술 | 프로젝트에서의 역할 |
|---|---|
| Python | Parquet 데이터를 읽고 과거 운행 기록을 시간 순서대로 이벤트화 |
| Apache Kafka | 지속적으로 발생하는 택시 운행 이벤트 수집 및 전달 |
| Spark Structured Streaming | Kafka 이벤트를 실시간으로 처리하고 지역·시간대별 지표 집계 |
| PostgreSQL | 운영 지표와 집계 결과를 SQL로 조회할 수 있도록 저장 |
| Parquet | 가공된 대량 운행 데이터를 분석용으로 저장 |
| Apache Airflow | 배치 집계의 스케줄링, 작업 의존성, 실패 작업 재시도 관리 |
| Docker / Docker Compose | Kafka, Spark, PostgreSQL 등 프로젝트 실행 환경 구성 |
| Open Source BI Tool | 지역·시간대별 운행 현황과 주요 운영 지표 시각화 |

기술 구성은 프로젝트 진행 과정에서 실제 구현 난이도와 데이터 처리 요구사항에 따라 조정할 예정이다.

## 7. 주요 사용 데이터

NYC TLC Yellow Taxi 데이터 중 프로젝트 목적에 필요한 주요 컬럼을 우선 사용한다.

| 컬럼 | 의미 | 활용 목적 |
|---|---|---|
| tpep_pickup_datetime | 승차 시간 | 운행 시작 이벤트 생성, 시간대별 수요 분석 |
| tpep_dropoff_datetime | 하차 시간 | 운행 완료 이벤트 생성, 운행 시간 계산 |
| PULocationID | 승차 지역 | 지역별 택시 수요 집계 |
| DOLocationID | 하차 지역 | 지역별 이동 및 하차량 집계 |
| trip_distance | 운행 거리 | 평균 운행 거리 등 운행 특성 분석 |
| fare_amount | 기본 운임 | 운행 요금 분석 |
| tolls_amount | 통행료 | 유료도로 이용이 포함된 운행 비용 확인 |
| total_amount | 최종 결제 금액 | 실제 운행별 총 결제 금액 분석 |
| payment_type | 결제 방식 | 운행 완료 데이터의 결제 정보 확인 |

승객 수와 팁 금액 등은 현재 프로젝트의 핵심 목표인 지역·시간대별 택시 운행 현황 파악과 직접적인 관련성이 낮다고 판단하여 우선 분석 대상에서 제외한다.
프로젝트를 진행하면서 필요한 지표가 추가될 경우 사용하는 컬럼을 확장할 예정이다.

## 8. Kafka 이벤트 설계 방향

원본 NYC Taxi 데이터는 이미 완료된 과거 운행 기록이므로, 이를 그대로 한 번에 처리하기보다 시간 순서대로 읽어 실제 택시 운행 이벤트가 발생하는 것처럼 재생하고자 한다.

하나의 택시 운행을 기준으로 우선 다음 두 가지 이벤트를 생성한다.

- trip_started : 승차 시점에 발생하는 운행 시작 이벤트
- trip_completed : 하차 시점에 발생하는 운행 완료 이벤트

두 이벤트는 하나의 택시 운행 과정에서 발생하는 연관된 이벤트이므로 우선 `taxi-trip-events`라는 하나의 Kafka Topic으로 관리하는 방향으로 설계한다.

이후 프로젝트를 확장하여 호출, 배차 수락, 결제 등 서로 다른 시스템에서 발생하는 이벤트를 다루게 된다면 Topic을 분리하는 방식도 고려할 수 있다.
